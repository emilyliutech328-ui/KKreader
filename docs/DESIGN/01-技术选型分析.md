# 双阅读 App 整合 · 技术选型分析（面向 Android）

> 分析对象：`legado-beta`（阅读Sigma，Kotlin 原生）× `Wenku8_Flutter-0.4.8`（Flutter/Dart）
> 分析方式：通读两套源码（解压至 `_extract\`），统计代码体量、依赖、耦合面与构建链，再按"整合要付的代价"倒推主框架。
> 日期：2026-10-25

---

## 0. 结论先说（TL;DR）

**主干选 Kotlin 原生（继续 KK读书 / legado-E 底座），不要用 Flutter 重做整个 App。**

三条硬理由：

1. **书源把主框架钉死在 JVM。** 书源规则引擎依赖 Rhino(JS)、jsoup、JsoupXpath、json-path、OkHttp/Cronet、WebView 反爬，JS 里还直接调 `java.ajax` 等 JVM 桥。搬到 Dart 等于重写整套 API 面并放弃存量书源生态——这是产品命根子，不能赌。
2. **你已经有可编译、可签名、可分发的 Kotlin 产物与流水线。** 切 Flutter 等于把 legado 12 万行 Kotlin 里除阅读器之外的部分（书架/分组/缓存/下载/书源管理/替换净化/订阅/朗读/Web API…）重写或桥接一遍，净亏。
3. **Wenku8 的能力 80% 可以低成本拿到。** 在线书库→做成内置书源（几天）；多格式导入→补原生解析器（1-2 周）；听书→加 edge-tts 引擎（1-3 周）。真正贵、且必须重写的只有 **竖排排版 / 对页 / 玻璃拟态视觉**——这三项放在最后一阶段，按需决策。

Wenku8 的正确用法不是"换框架"，而是"当成需求清单 + 算法参考 + 可选阅读页模块"。

## 3. 为什么书源决定了主框架必须是 JVM

规则引擎实际分布（`app/src/main/java/io/legado/app/`）：

```
model/analyzeRule/  AnalyzeRule.kt 34KB   AnalyzeUrl.kt 32KB
                    AnalyzeByJSoup 18KB   RuleAnalyzer 14KB
                    AnalyzeByXPath 5KB    AnalyzeByJSonPath 6KB
                    AnalyzeByRegex 2KB    QueryTTF 38KB（字体混淆解密）
model/webBook/      WebBook 18KB  BookChapterList 14KB  BookList 13KB
                    BookContent 12KB  SearchModel 8.7KB  BookInfo 7.4KB
help/JsExtensions.kt、help/webView/WebJsExtensions.kt → 暴露 java.ajax / java.get / cookie 等 JVM API
modules/rhino/      自研 Rhino ScriptEngine（RhinoScriptEngine 16KB、ExternalScriptable 10KB、JSAdapter 10KB、RhinoClassShutter 6.6KB 等 31 个类）
```

要搬进 Dart，需要：HTML/XML 解析（Dart 有 `html`/`xml`）、XPath（有第三方）、JSONPath（有）、正则（原生）、**JS 引擎 + 一整套 `java.*` 兼容桥（QuickJS 重写）**、cookie/证书/WebView 反爬、字体混淆解密。工作量以月计，且只要是"兼容存量书源"就得持续回归——收益却是"把已经能跑的引擎重写一遍"。

**所以：引擎留在 Kotlin。**

## 4. 为什么竖排/对页/视觉是 Wenku8 的真资产

阅读器 Dart 文件体量（KB）：`reader_tools 67`、`reader_paged_view 64`、`reader_pagination 28.6`、`reader_illustrations 27`、`reader_vertical_text 26.5`、`reader_selection 15`、`reader_scroll_stream 14.8`、`reader_content 14.5`、`reader_rich_content 13.7`、`reader_turn_motion 12.9`、`reader_find 12.1`、`reader_reflow 10.9`、`reader_line_reflow 10.6`、`reader_spine_turn 9.8`——合计约 350KB Dart，约 1 万行"文字排版手感"。

这些在原生里重写要付出：CJK 竖排断行与标点旋转、避头尾、注音 ruby、选区坐标映射、从右至左翻页、对页书脊、曲面翻页物理、字体度量。**这是全项目最贵的单项（20-40 人天起，且质量看机型适配）**。

但它的耦合也很实在：`reader_paged_view.dart` 直接 import `library_state.dart`(96KB)、`reader_preferences`、`reader_content/pagination/turn_motion/spine_turn/illustrations`；`reader_tools.dart` 还 import `library_state`、`local_platform`、`book_documents`、`font_settings_page`。**想"整块搬走"必须先抽数据层**，这也解释了为什么混合方案没想象中便宜。

## 5. 两条路线的成本对比（人天，单人熟手，±50%）

### 方案 A：Kotlin 主干 + 分层移植（推荐）

| 工作包 | 人天 |
|---|---|
| A1 文库在线书源（发现/排行/搜索/详情/目录/正文/登录 cookie） | 3–7 |
| A2 多格式解析器：DOCX / RTF / FB2 / MD / HTML / ZIP | 10–15 |
| A3 edge-tts 朗读引擎（WS 流式 + SSML + 音色列表 + 预缓存 + 系统 TTS 回落） | 5–10 |
| A4 书签分类 + 选句分享图 | 5–8 |
| A5 系列/分卷 + 批量整理 | 5–8 |
| A6 局域网续读（NanoHTTPD 已有） | 8–12 |
| A7 对页/双栏 + 翻页动效增强 | 5–10 |
| **P0–P3 小计（不含竖排/玻璃）** | **≈ 45–70** |
| A8 竖排（原生重写，高风险） | 20–40 |
| A9 玻璃拟态/动效（Compose + RenderEffect，效果打折） | 10–20 |

### 方案 B：Flutter 主干 + legado 引擎 AAR

| 工作包 | 人天 |
|---|---|
| B1 抽引擎成 AAR（剥离 Room/UI/LiveEventBus/Application 耦合） | 15–25 |
| B2 MethodChannel/FFI 数据桥（大文本、超时、日志、并发） | 10–15 |
| B3 书源管理 UI 重做（列表/编辑/导入/校验/调试日志/替换净化/订阅/发现） | 25–40 |
| B4 书架/分组/缓存/下载/进度迁移 | 15–25 |
| B5 与 Wenku8 数据模型统一（本地书/在线书/书签/系列/进度） | 15–25 |
| B6 联调回归 + 发版 | 15–20 |
| **合计** | **≈ 95–150** |

隐性成本：放弃现有 KK读书 定制与流水线；包体 +12–18MB；冷启动 +300–600ms；minSdk 21→约 24；Gradle/Kotlin 版本要统一（legado 用 Kotlin 2.3.10/AGP 8.13.2，Wenku8 用 Kotlin 2.2.20/AGP 8.11.1，且 Flutter Gradle Plugin 有应用顺序约束）。

### 方案 C：混合 add-to-app（Kotlin 宿主 + Flutter 只做阅读页）

POC 4–6 周，稳定可用 3 个月+。两套 UI/状态/主题/手势长期并存，维护成本最高。**定位：只在"竖排+玻璃视觉"被判定为刚需时，作为 A8/A9 的替代**——比整体倒向 Flutter 便宜得多。

## 6. 推荐架构（方案 A）

```
┌──────────────────────────── KK读书（Kotlin） ────────────────────────────┐
│ UI 层   View(现有) + Compose 增量(新页面：发现/本地书库/设置/听书)         │
├──────────────────────────────────────────────────────────────────────────┤
│ 引擎层  model/analyzeRule + model/webBook + modules/rhino + OkHttp/Cronet │
│         ← 新增：内置书源 assets/defaultData（cn.wenku8）                   │
├──────────────────────────────────────────────────────────────────────────┤
│ 数据层  Room（Book/BookChapter/Bookmark…，bookmark 增 category 字段）      │
├──────────────────────────────────────────────────────────────────────────┤
│ 本地书  LocalBook 子类：TextFile/EpubFile/MobiFile/PdfFile/UmdFile         │
│         ← 新增：DocxFile/RtfFile/Fb2File/MarkupFile/ArchiveBundle         │
├──────────────────────────────────────────────────────────────────────────┤
│ 服务层  TTS/朗读、缓存、下载、WebService ← 新增 EdgeTtsEngine(WS+SSML)     │
└──────────────────────────────────────────────────────────────────────────┘
```

关键做法：
- **文库做成"内置书源"而不是硬编码**：走现有 BookSource 流程，可热更新、可在 App 内编辑、不污染数据模型；登录态用现成 CookieStore。
- **新格式一律实现 `BaseLocalBookParse` 子类**，落成章节 + 文本，复用现有阅读/进度/书签/缓存全套能力。
- **书签分类**只加字段 + Room migration，不动 UI 主干。
- **听书**抽象成"在线 TTS 引擎"，与现有 HTTP TTS 并列，失败自动回落系统 TTS。

## 8. 技术坑位清单

1. **jsoup 锁定 1.16.2**：上游注释写明 1.17+ 的破坏性变更会影响 `AnalyzeByJSoup` 与 JsoupXpath；别顺手升级。
2. **Rhino 锁 1.8.1**：新版用了 Android 8 以下没有的 `VarHandle`。
3. **POI 体积**：`poi-scratchpad + poi-ooxml` 对 dex/包体影响大，建议只取 DOCX 需要的模块，或用 `xml + zip` 自写轻量 docx 解析（Wenku8 的 Dart/Kotlin 实现可作参考）。
4. **edge-tts 不稳定**：微软 WS 接口随时可用性波动、国内网络差 → 超时 + 系统 TTS 强制回落，别做成唯一朗读。
5. **竖排是深坑**：标点旋转与位置、避头尾、注音 ruby、选区坐标映射、右→左翻页、插图浮排，逐项都是适配量。
6. **许可**：两者都 GPL → 合并产物必须 GPL-3.0 开源可获取；闭源分发不合规。这条建议在产品层面先想清楚。
7. **内置书源版权/反爬**：文库内容与封面归权利人；登录态、限流、付费章节要按站点规则处理，别绕过访问限制。
8. **混合构建**：若走方案 C，需统一 Gradle/Kotlin/AGP，并遵守 Flutter Gradle Plugin 的应用顺序；`.so` 要 16KB 对齐（Wenku8 的 CMake 已加 `-z max-page-size=16384`）。

## 10. 还需要你拍板的三件事

1. **竖排 + 玻璃拟态是不是核心竞争力？**（目标用户是否日轻/文库读者）
